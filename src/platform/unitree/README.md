# Unitree ROS 2 Go bindings

The two public Go modules live in `include/u2rosv2/universal/go` and `include/u2rosv2/platform/unitree/go`. The first declares all 163 registered `uwvm_ros_v2` operations. The second provides the 43 messages in Unitree ROS 2 v0.3.0 as ordinary Go structs. Source package names are `unitreeapi`, `unitreego` and `unitreehg`. The generator preserves signedness, field order, fixed arrays, sequence element types and nested message types. Struct tags carry the original ROS field names.

Both `unitreego.LowState` and `unitreehg.LowState` have `MarshalCDR(dst, order)` and `UnmarshalCDR(src)`. They accept plain DDS CDR1 with a four-byte CDR_BE or CDR_LE encapsulation and zero options. Generated codecs align fields from the start of the serialized body. Go2 uses 20 nested MotorState records and a 1,180-byte encapsulated frame. HG uses 35 and a 2,092-byte frame. Both layouts include the IMU, fixed arrays, reserved fields and CRC. The CRC travels as payload. Other message types currently provide Go storage only.

The Unitree SDK2 2.0.2 C++ headers and the ROS 2 messages differ in two Go2 temperature fields. The DDS C++ class uses unsigned bytes for temperature_ntc1 and temperature_ntc2. The ROS 2 package uses int8, which these Go bindings preserve. The existing scene driver contract `unitree/go2/low-state/v1` delivers a 16-byte projection containing the tick and one joint position. A deployment providing a complete serialized ROS 2 sample can pass its CDR bytes directly to UnmarshalCDR. [Unitree ROS 2](https://github.com/unitreerobotics/unitree_ros2/tree/66ae09858245ac3d2231c0cc209e36a88f8d7d03/cyclonedds_ws/src/unitree) [Unitree SDK2 LowState](https://github.com/unitreerobotics/unitree_sdk2/blob/811bc77cdcffb4691d4b40172f9a57857bf6cffb/include/unitree/idl/go2/LowState_.hpp)

Regenerate the public source with `python3 -B src/platform/unitree/generate_go.py` and `python3 -B src/compilers/go/generate_abi.py` from the checkout with gofmt on PATH. The installed external Xmake applications for standard Go and TinyGo have byte-identical main.go and go.mod files. They call the VM's ABI operation and exercise both endiannesses with locally constructed numeric fields. Their result describes the codec and VM call. Hardware and DDS acquisition require a separately provisioned deployment.
