# Qualifying a platform binding

Each task owns one named platform. Development uses GPT-6.2 Astra with max reasoning at default speed. After the developer freezes its commit and ends, the integration lead assigns a GitHub candidate with the same source tree to a fresh GPT-6.2 Sol task using max reasoning at default speed. Sol records the outcome and ends before a fresh Astra task takes over a fix. A passing result covers the upstream revision, language, compiler configuration and interfaces exercised in that run.

For each platform, identify the manufacturer's libraries, protocols, driver and upstream examples. Record their upstream URLs, versions and complete commits. Identify manufacturer interfaces, driver interfaces and community ports separately. Compare public symbols and driver registrations for namespaces, types, constants, units, field order, service requests and replies, action stages, errors, version differences and required grants. The guest uses capabilities issued by the VM. The host driver owns controller connections, authentication and device lifecycle.

Each target language needs the same typed platform surface, idiomatic reference documentation and an external Xmake project. Check every language selection in the universal catalog. Track aliases and interoperability bridges separately. Record the dependency for any missing compiler, interpreter or runtime. Track source availability, actual Wasm compilation, independent wire compatibility, INT/AOT execution and vendor simulation separately.

Install from GitHub using the root installer, a pinned commit and empty home and cache directories. Build and run offline inside a namespace after downloading. Run tests outside the coordinator's cgroup. The parent test slice and its test subgroup must both have a 64 GiB memory limit and zero swap. Exercise the installed compiler and Xmake separately from an external project. Record the source revision, module digest, run configuration and assertions. A single-field example qualifies the field and paths it exercises.

For every language on every vendor platform, fetch the installer and selected toolchain from GitHub and compile and run an external project. A vendor passes only when all its target languages complete this path.

## First ABB baseline

The four ABB ROS 1 interface packages contain 25 messages and 22 services. Each service has a request and a response. RAPID data, EGM feedback, system state and StateMachine settings belong to distinct APIs. Additional standard ROS messages, services and actions are counted under their own libraries. The RobotWare version, StateMachine Add-In and controller options affect which services the driver registers. The ROS 2 interface definitions come from a separate community port and require independent CDR qualification. [ROS 1 definitions](../../src/platform/abb/upstream/ros1/) · [ROS 2 definitions](../../src/platform/abb/upstream/ros2/) · [Driver registrations](../../src/platform/abb/upstream/abb_robot_driver/)

Separate pins identify the native EGM protocol, the RWS client and the EGM/RWS managers. The manufacturer's EGM protobuf messages and the library's wrapper messages have separate definitions. Qualifying a ROS message updates the result for that interface. ABB also publishes distinct product interfaces, including RWS for RobotWare 7 and 8 and PC SDK. Their individual bindings and runtime environments still need implementation and qualification.
